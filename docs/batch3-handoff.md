## Contract sources and discrepancies

The official [Geoapify Routing OpenAPI specification](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/routing/routing-api-openapi-specs.json) is version 1.2.0 from commit [`e8255e614648084d86bae2155c20347d5203ec1d`](https://github.com/geoapify/geoapify-openapi-specs/tree/e8255e614648084d86bae2155c20347d5203ec1d), reviewed 2026-09-30. Its SHA-256 is `3befa20ade08b308cc4551c1dec47174e217193e142e78a23fbdd83263f114ca`. The captured catalog bytes have SHA-256 `31f3735da9e209ed850edcba3ba4e29f52ee424970210bd04a757e65d57eaea2`; this differs from the Batch 2 catalog bytes and does not by itself establish changed API semantics. The [human Routing documentation](https://apidocs.geoapify.com/docs/routing/) was reviewed on the same date.

Recorded differences: OpenAPI authentication offers both `apiKey` query and `x-api-key` header; human examples use query authentication, and this package uses the supported header credential. Human documentation describes `lonlat` as an alternative waypoint form, while the schema pattern supports only plain `latitude,longitude`; the UI uses separate latitude and longitude controls and sends the schema form. Schema bounds the waypoint count at 2–1,000 while human prose says only two or more; use the schema maximum. The response `details` enum includes `admin_areas`, while the request `details` enum and human parameter prose omit it. Human instruction fields use camelCase (`exitNumber`, `exitRoadName`, `exitTowards`) while schema fields use snake_case. Preserve returned properties without translation and do not expose response fields as request controls.

OpenAPI and human documentation establish the contract review only. They do not establish live API acceptance, account entitlements, credits, quotas, or actual error behavior. Do not infer semantics changed merely because the captured catalog digest differs from an earlier batch's copy.

## Implementation style and output contract

The operation uses declarative n8n routing for its ordinary REST GET, with the fixed URL `https://api.geoapify.com/v1/routing`, the package's existing credential injection, and the host routing system. Its callback validates inputs before `makeRoutingRequest` and handles and sanitizes request failures; `postReceive` validates the GeoJSON FeatureCollection and normalizes output. Existing n8n core 2.30.3 evidence explains the callback validation and error handling: `preSend` validation failures bypassed the callback's error catch. The fixed URL, expressions, and existing hooks cover this operation without custom `execute`, custom transport, runtime dependencies, environment access, or filesystem access.

Controls include the native ordered fixed collection `waypoints={waypoint:[{latitude,longitude}, ...]}` and a travel mode selector defaulting to `drive` with all 17 documented modes. Individual coordinates support expressions. A mutually exclusive JSON mode (`waypointMode=json`, required `waypointsJson`) accepts an ordered array as JSON text or an array-valued expression. Validation enforces the expected collection shape and count of 2–1,000; finite numeric values; latitude bounds -90..90; longitude bounds -180..180; and accepts zero. Each waypoint serializes as `latitude,longitude`, joined with `|`. Each input makes one request with `units=metric`, `format=geojson`, a 30-second timeout, and no automatic retry. Advanced optional selectors are not exposed.

Default output is one linked item containing the complete route Feature with geometry, `id`, `bbox`, all properties, and legs preserved, plus `_geoapifyUnits: { distance: "meters", duration: "seconds" }`. Raw output is the complete FeatureCollection per input, with no added unit metadata. Route distances use meters and durations use seconds. An empty FeatureCollection yields zero items in default feature mode and one empty collection item in raw mode. Native **Always Output Data** may add its configured empty `{}` item at the workflow boundary for default feature mode.
