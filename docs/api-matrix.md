# Geoapify API and operation matrix

This document limits the package to independently useful, documented operations. OpenAPI contracts establish request/schema evidence; they do not establish live API behavior or a user's account entitlements.

## Contract sources and discrepancies

The official [OpenAPI catalog](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/index.json) was checked first on 2026-09-30. Batch 1 loaded its two specifications; Batch 2 loaded only the Places and Place Details specifications listed below. All four are pinned to Geoapify's OpenAPI repository commit [`e8255e614648084d86bae2155c20347d5203ec1d`](https://github.com/geoapify/geoapify-openapi-specs/tree/e8255e614648084d86bae2155c20347d5203ec1d): [forward geocoding spec](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/forward-geocoding/forward-geocoding-api-openapi-specs.json) and [reverse geocoding spec](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/reverse-geocoding/reverse-geocoding-api-openapi-specs.json), [Places spec](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/places/places-api-openapi-specs.json), and [Place Details spec](https://github.com/geoapify/geoapify-openapi-specs/blob/e8255e614648084d86bae2155c20347d5203ec1d/api-specs/place-details/place-details-api-openapi-specs.json). Batch 2 spec files were accessed 2026-09-30; SHA-256 digests are in [the Batch 2 handoff](batch2-handoff.md).

Human documentation reviewed on the same date: [catalog](https://apidocs.geoapify.com/docs/), [forward geocoding](https://apidocs.geoapify.com/docs/geocoding/forward-geocoding/), [reverse geocoding](https://apidocs.geoapify.com/docs/geocoding/reverse-geocoding/), [Places](https://apidocs.geoapify.com/docs/places/), and [Place Details](https://apidocs.geoapify.com/docs/place-details/). Their explanatory prose and embedded generated API reference were considered separately; where a parameter appears only in the embedded reference/schema and not in the human-facing parameter prose, that distinction is recorded below. The implementation-style decision follows n8n's guidance on [node overview](https://docs.n8n.io/connect/create-nodes/overview/), [choosing a node-building style](https://docs.n8n.io/connect/create-nodes/plan-your-node/choose-a-node-building-style/), and [verification guidelines](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/verification-guidelines/), accessed 2026-09-30.

Recorded differences: the contracts define both `ApiKeyInQuery` (`apiKey`) and `ApiKeyInHeader` (`x-api-key`) security schemes, while human prose/examples show query authentication; this integration uses the supported `x-api-key` header through n8n credentials. The contract models filters and bias values as arrays in places where human examples serialize them as strings; Batch 1 sends the forward country restriction as `filter=countrycode:<comma-separated-codes>`, as described in the forward documentation's prose filter section. The reverse schema and embedded reference include locality/building as parameter enum values absent from the reverse human-facing parameter list, so those choices are not exposed. Country restriction is forward-only in the UI; the shared form does not send it on reverse requests. The response wrapper is modeled as a GeoJSON FeatureCollection.

No live Geoapify request has yet confirmed these contracts against an account. Do not infer plan availability, exact rate limits, postal deliverability, or observed error bodies from the schema or tests.

All operations use the same declarative REST routing design. The selected operation supplies a fixed absolute URL expression. A routing callback validates values before `makeRoutingRequest`, then catches and sanitizes transport errors so Continue On Fail can return a paired error item; this preserves behavior that a `preSend` hook could not provide in n8n core 2.30.3 because `preSend` failures bypassed the callback's catch. `postReceive` validates and normalizes the response. Geocoding and Place Details make one request per input. Places Search uses the routing pagination hook with explicit request/result caps and termination checks. No custom `execute` or custom transport is used. Expressions are supported in fields/options. The node does not define a generic API operation. n8n's host loader may add a separate Custom API Call menu entry for generic-auth credentials; that affordance is host-provided. The node defines no `requestDefaults`, leaving each selected endpoint URL explicit.

### Shared authentication and output contract

The single `Geoapify API` credential stores a password-masked API key and injects `x-api-key` in the request header. Runtime code must not read environment variables or the filesystem. The node uses the credential for both operations. The credential test is a documented GET to `/geocode/search?text=Berlin&limit=1`. Geoapify's forward and reverse pricing sections state that one request equals one credit, so this credential test consumes one credit.

The node's selected output is either one item per returned feature or one item containing the raw FeatureCollection. In feature mode, the response's `properties` are copied to top-level `json`, while `geometry` is retained. This carries service-returned IDs, formatted/structured address values, coordinates, rank and confidence values through without claiming that confidence guarantees postal deliverability. In one-item-per-match mode, a successful FeatureCollection with no features maps to `[]`; this is successful empty output, not an API error or fabricated feature. In raw mode, every input produces one item containing the full FeatureCollection, including an empty `features` array. Native n8n **Always Output Data** affects the empty per-match mode, where it may add its configured empty item at the workflow boundary. Multiple matches are never reduced to an arbitrary first match. In the pinned n8n routing fixture, two inputs produced four results with paired-item indexes `0,0,1,1` for successful results and `0,1,1` for one Continue On Fail error and two successful results, confirming linkage in those tested paths; see [testing evidence](testing.md).

### Geocoding and Place Details request limits and failure behavior

Geocoding and Place Details requests have a 30-second timeout; their callback makes at most one request per input item and does not retry. Places Search is separately bounded by the request/result caps in its row and may make multiple offset requests. No operation retries automatically. Users may configure bounded n8n Retry On Fail behavior for their plan and workflow. Error handling retains useful service messages and sanitized rate-limit timing where available, while excluding credential values and authenticated URLs. The API's exact account-specific quota and rate-limit limits remain outside this contract.

The category enum in the pinned Places contract contains 833 keys. Comparison with the captured human Places category table/text has 20 enum keys absent: `traffic_signals`, `natural.water.inland`, `natural.water.moat`, `continent`, `island`, `power.tower`, `power.pole`, `power.portal`, `power.switch`, `power.catenary_mast`, `power.cable`, `power.terminal`, `power.insulator`, `power.heliostat`, `power.connection`, `power.inverter`, `power.converter`, `power.compensator`, `power.circuit`, and `tourism.sights.square`. Category membership in the spec is not proof of live acceptance. Human prose says country filtering is coming soon while the schema models it, so no country filter is exposed. The Details schema describes `features` as pipe-separated while human reference text describes commas; this selector is omitted because Details requests the default set. The human Details page enumerates six geometry kinds while its response schema also includes GeometryCollection; preserve returned geometry without narrowing.

## Deliberately deferred

This batch does not implement autocomplete, asynchronous batch geocoding, Routing, matrices, route optimization, isolines, map matching, static maps, tiles, elevation, geometry operations, MCP, or triggers. Routing remains Batch 3; release-readiness work remains Batch 4. Other listed operations remain deferred.
